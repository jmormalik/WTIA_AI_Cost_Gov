# AI 비용·게이트웨이 주장에 대한 심층 팩트체크 보고서

이 보고서는 스타트업 피치덱에 포함된 다섯 개의 핵심 주장, 즉 C2(“AI 원가의 41%가 비‑LLM”), C3(“무한 루프로 11일간 4만7천 달러 청구”), C4(“하룻밤 사이 API 비용 400% 급증”), C9a(“Langfuse·Helicone은 추적만 하고 실행 전 차단 불가”), C10(“SatGate는 프리론칭 상태”)를 대상으로 한다. 우리는 공개적으로 검증 가능한 1차·2차 출처를 재검색하여, 각 숫자와 기능 주장이 실제 문서에 존재하는지, 2026년 기준으로 여전히 유효한지, 그리고 경쟁사 관련 기술 묘사가 해당 업체 공식 문서와 충돌하지 않는지를 면밀히 검토했다. 그 과정에서 LLM 비용 구조에 대한 공개 벤치마크, AI 비용 초과에 관한 대규모 설문조사, 실사고 사례(Agent 무한 루프, API 키 탈취, LLMjacking 공격), 그리고 Cloudflare AI Gateway 및 LangSmith LLM Gateway와 같은 최신 런타임 게이트웨이 문서를 교차 분석했다.[1][2][4][5][6][8][9][10][14][15] 분석 결과, 다섯 주장 가운데 하나(C3)는 출처가 존재하는 실사고 일화로서 안전하게 인용 가능한 반면, 둘(C2·C4)은 구체 숫자 수준에서는 외부 출처로 뒷받침되지 않아 “합의 숫자”처럼 말하기에는 위험하며, 둘(C9a·C10)은 2026년 현재의 경쟁사 기능·시장 상황을 충분히 반영하지 못해 전략적 포지셔닝 관점에서 구식으로 분류되었다. 결론 부분에서는 투자자 Q&A에서 창업자가 안전하게 사용할 수 있는 재서술 문장을 제시하며, 각각의 주장에 대해 CONFIRMED, WRONG, UNVERIFIABLE, OUTDATED 네 가지 판정 범주 중 어디에 놓이는지 정리한다.

## 1. 팩트체크 접근 방법과 자료 출처

### 1.1. 검증 대상과 판정 기준

본 팩트체크는 특정 피치덱의 세 장(슬라이드 [3], [4], [7])에 포함된 핵심 메시지들 중, 선행 분석에서 이미 “근거 없음 또는 반증됨”으로 표시된 네 개 클러스터(C2, C3, C4, C9a, C10)를 재검증하는 데 목적이 있다. 선행 분석이 제시한 1차 판정에 그대로 의존하지 않고, 각 주장을 독립적으로 다시 검색해 교차 검증하는 것이 본 보고서의 출발점이다. 이를 위해 우리는 제공된 검색 결과 집합(총 18개)을 체계적으로 분류하여, 비용 구조 관련 자료, 사고·공격 사례, 설문조사·시장 리포트, 그리고 런타임 게이트웨이 및 벤더 기술 문서로 나누어 살펴보았다.[1][2][4][5][6][8][9][10][14][15] 특히 숫자가 포함된 주장에 대해서는 “그 숫자가 실제로 해당 출처에 명시되어 있는지”라는 점을 최우선으로 검토했고, 기능·경쟁사 관련 주장에 대해서는 해당 벤더 공식 문서와의 정합성을 중점적으로 살폈다.

판정은 네 가지 범주로 구분했다. 첫째, CONFIRMED는 주장의 핵심 숫자·사실이 하나 이상의 신뢰할 만한 출처에 명시되어 있고, 해석상의 큰 왜곡이 없는 경우를 의미한다. 둘째, WRONG은 특정 숫자나 기능 묘사가 “출처로 제시된 문서와 명백히 불일치”하거나, 다른 공신력 있는 자료가 동일한 사실을 반박할 때 적용한다. 셋째, UNVERIFIABLE은 외부 1차·2차 출처에서 해당 숫자나 사건이 발견되지 않거나, 증거가 너무 빈약해 “사실로 단정하기 어렵지만, 틀렸다고 단정할 수도 없는” 중립 상태를 가리킨다. 넷째, OUTDATED는 주장이 과거 특정 시점에서는 사실이었지만, 2026년 시점에는 기술·시장 환경 변화로 인해 더 이상 현재를 정확히 반영하지 못하는 경우에 사용했다. 이 네 범주는 단순히 “맞다/틀리다”의 흑백 논리가 아니라, 투자자 Q&A에서 창업자가 어느 정도까지 자신 있게 발언할 수 있는지를 가늠하는 실용적 안전선으로 이해되어야 한다.

### 1.2. 자료 신뢰도와 한계

자료 신뢰도 측면에서, 우리는 여러 유형의 출처를 구분하여 평가했다. 학술 논문과 대형 리서치 기관 보고서는 통상 엄격한 방법론을 따르므로, 특정 수치나 경향을 인용할 때 상대적으로 높은 신뢰도를 부여했다. 예를 들어, 2026년 5월 발표된 arXiv 논문 “Agentic AI Workload Characteristics”는 다양한 에이전트 벤치마크에서 LLM 추론과 툴 호출의 실행 시간 비중을 체계적으로 계측한 실험으로, 시간 분해에 대한 언급에는 높은 신뢰를 부여할 수 있다.[2] 반면, 벤더 블로그나 마케팅 성격의 콘텐츠는 방법론이 부분적으로 생략되어 있거나 자사 제품에 유리한 사례를 중심으로 구성되므로, 수치 인용 시 그 문맥과 전제 조건을 함께 살펴야 한다. Cockroach Labs의 “Agentic AI 비용” 블로그가 “LLM 추론은 TCO의 약 20%에 불과하다”는 주장을 담고 있지만, 이 수치가 어떤 유형의 고객·워크로드를 기반으로 한 것인지 구체 공개가 없어, 다른 벤더의 숫자와 직접 비교하기에는 조심스러워야 한다.[4]

사고·공격 사례의 경우, 당사자가 Medium, Towards AI, dev.to와 같은 플랫폼에 올린 경험담은 “실제 발생한 일”을 간접적으로 보여주지만, 인보이스나 로그가 외부에서 독립적으로 검증된 것은 아니므로 숫자 정확성을 절대적인 것으로 받아들이기 어렵다. 무한 루프 에이전트로 4만7천 달러를 사용했다는 Teja Kusireddy의 글이 바로 이 범주에 속한다.[5][13] 그러나 동일 사건을 여러 매체가 재인용하고, 서술에 내적 일관성이 있을 경우, 이를 “대표적 위험 사례”로 언급하는 것은 투자자 커뮤니케이션 측면에서 의미가 있다. API 키 탈취로 이틀 동안 8만2천 달러를 청구당한 Gemini 사용자의 사례처럼, Tom's Hardware와 같은 메인스트림 IT 매체가 피해자 증언과 함께 보도한 사건은 보다 높은 신뢰도를 가진다.[6]

또 하나의 한계는 검색 결과가 Helicone, Langfuse, SatGate, Revenium과 같은 특정 벤더의 공식 문서를 직접 포함하고 있지 않다는 점이다. 제공된 검색 결과 안에는 Cloudflare AI Gateway와 LangSmith LLM Gateway 같은 대표적인 런타임 게이트웨이 문서가 포함되어 있지만, Helicone 및 SatGate에 관한 공식 문서는 포함되어 있지 않다.[14][15] 따라서 이들 벤더 기능에 대한 구체적인 판정은 “내부적으로 알고 있는 사실”에 기대지 않고, 제공된 결과 범위 안에서만 할 수 있는 것에 제한된다. 본 보고서는 “절대 URL·발행일·제목을 새로 만들어내지 않는다”는 원칙을 지키기 위해, 제공된 결과에 등장하지 않는 문서의 날짜·주소·정확한 기능 세부사항은 언급하지 않는다. 그 대신, 우리가 확실히 검증할 수 있는 대형 게이트웨이·관측성 벤더의 기능과 비교하여, 특정 주장(C9a, C10)이 2026년 시장 현실과 얼마나 어긋나는지를 평가한다.

### 1.3. 2026년 맥락에서 “구식”을 판정하는 기준

일부 주장은 2025년 당시에는 사실이었으나, 2026년에 들어 기술·서비스가 빠르게 진화하면서 더 이상 정확한 묘사가 아니게 되었을 가능성이 있다. 이를 평가하기 위해 우리는 시간 축을 명확히 인식했다. 예를 들어, Cloudflare AI Gateway의 런타임 지출·요청 한도 기능은 2026년 중반 문서에 명시적으로 등장하며, 한도를 초과하는 요청에 대해 429 에러를 반환하여 upstream LLM 제공자까지 요청이 전달되지 않도록 차단한다고 설명한다.[14] LangSmith LLM Gateway 역시 2026년 블로그에서 비용·속도·한도를 런타임에서 통제하는 기능을 소개하며, 지출 상한을 넘긴 요청에는 402 응답으로 “실행 자체를 막는다”고 밝힌다.[15] 이러한 기능이 출시되기 전에는 “실행 전 차단을 하는 게이트웨이는 없다”는 유형의 주장도 어느 정도 사실에 가까웠겠지만, 출시 이후에는 더 이상 사실이라고 보기 어렵다.

따라서 OUTDATED 판정을 내릴 때에는 두 가지를 보았다. 첫째, 해당 주장이 의존하는 사실이 특정 연도·분기에만 유효했는지, 둘째, 현재 시점에서 공개적으로 이용 가능한 자료가 그 사실을 대체·반박하는지 여부이다. 예를 들어 C9a에서 “Helicone·Langfuse 같은 관측성 툴은 추적만 하고 실행 전 차단 기능은 없다”는 식의 서술은, Cloudflare AI Gateway와 LangSmith LLM Gateway가 이미 실행 전 차단을 제공하는 상황에서는 “시장 전체에 대한 묘사”로서 구식이다.[14][15] Helicone·Langfuse 자체에 대한 기능 판정은 제공된 검색 결과로는 할 수 없지만, “아무도 실행 전 차단을 하지 않는다”는 메시지 줄기는 2026년에는 더 이상 현재를 묘사하지 못한다.

## 2. LLM 비용 구조와 에이전트 워크로드에 대한 공개 데이터

### 2.1. 시간 기준 분해: LLM vs 툴 호출

C2 주장의 배경을 이해하기 위해서는 LLM 에이전트 워크로드에서 “모델 호출”과 “툴 실행”이 실제로 어떻게 시간을 분배하는지부터 살펴봐야 한다. 2026년 5월에 공개된 논문 “Agentic AI Workload Characteristics”는 DABStep, GAIA, SWE-bench Pro, Terminal-Bench 등 다양한 에이전트 벤치마크를 대상으로 LLM 추론과 도구 호출의 실행 시간을 계측했다.[2] 이 논문에 따르면, 모든 벤치마크와 모델을 통틀어 에이전트 실행은 대부분 LLM 지배적이며, LLM 추론이 전체 실행 시간의 71%에서 98%까지를 차지했다는 결과가 보고된다.[2] 반대로 툴 실행은 전체 시간의 2%에서 29% 정도로 나타났으며, 가장 툴 비중이 높은 워크로드는 GAIA로서 웹 검색·웹 페치 중심 도구 호출 때문에 Gemma Thinking 모델 기준 28.7%, Qwen Thinking 기준 24.9%까지 툴 시간이 상승했다.[2] SWE-bench Pro와 Terminal-Bench 역시 Bash·Read·Edit·Agent·TaskOutput 등 다양한 툴에 의존하기 때문에 각각 17.7%, 17.6% 수준의 툴 호출 시간을 기록했다.[2]

논문은 LLM 실행 자체를 다시 프리필(prefill)과 디코드(decode) 단계로 나누어 분석하는데, 모든 벤치마크에서 LLM 실행은 강하게 디코드 지배적이다.[2] 디코드 단계가 LLM 실행 시간의 91.0%에서 98.6%까지를 차지하며, 프리필은 1.4%에서 9.0%에 불과하다.[2] 이는 대부분의 입력 토큰이 여러 턴에서 재사용되면서 높은 캐시 히트율(84.6%에서 99.5%)을 기록하기 때문이며, 결과적으로 LLM 추론 시간의 대부분은 새로운 토큰을 생성하는 디코딩 작업에 집중된다.[2] 이 실험은 “시간 기준”이라는 점에서 비용 구조와 직접적으로 일치하지는 않지만, 최소한 “에이전트 실행 시간의 절반 이상이 LLM 추론에 쓰인다”는 패턴을 강하게 시사한다.

이러한 시간 분해 결과에서 중요한 것은 “툴 실행이 결코 무시할 수 없는 비중을 차지하지만, 대부분의 워크로드에서 LLM 추론이 여전히 지배적이다”라는 균형이다. 웹 검색에 의존하는 GAIA 같은 워크로드에서는 툴 실행 비중이 최대 28.7%까지 올라가지만, 그렇다고 해서 “LLM 추론이 59%, 검색이 24%, DB가 17%”라는 식의 특정 숫자 분해가 자연스럽게 도출되는 것은 아니다.[2] 논문은 데이터베이스 호출을 별도의 카테고리로 분리하지도 않고, 비용이 아니라 시간 관점에서만 분석하기 때문에, C2에서 제시된 “59/24/17”은 적어도 이 논문에서 나온 숫자가 아니다.

### 2.2. 비용 기준 분해: 추론 비용 vs 주변 비용

시간 분해와 달리, 비용 구조를 다루는 공개 자료들은 “LLM 추론이 전체 TCO에서 어느 정도의 비율을 차지하는지”를 다양한 관점에서 서술한다. Cockroach Labs의 블로그 “The Bill Arrives: How to Manage Agentic AI Costs at Scale”는 많은 조직이 AI 비용을 과소평가하는 이유를 설명하면서, 실제로는 추론(inference) 비용이 전체 TCO의 약 20%에 불과하다고 주장한다.[4] 이 블로그에 따르면, 나머지 80%는 오케스트레이션 레이어(플래닝, 리트라이, 툴 사용, 상태 관리), 평가·모니터링, 데이터 준비·RAG 인덱싱, 인프라·라이센싱 등 모델 주변에 존재하는 다양한 비용으로 구성된다.[4] 특히 스탠퍼드 Digital Economy Lab의 “Agentic AI Cost Attribution, 2025” 연구를 인용하면서, 재전송되는 컨텍스트가 전체 에이전트 추론 비용의 62%를 차지한다는 점을 강조한다.[4] 즉 많은 비용이 “모델이 이미 알고 있는 내용을 다시 읽는 것”에 쓰인다는 것이다.[4]

커스텀 LLM 애플리케이션 구축 비용을 분석한 TechAhead의 2026 보고서 역시 비슷한 메시지를 담고 있다.[3] 이 보고서는 엔터프라이즈 용도에서 커스텀 LLM 개발 프로젝트의 전체 비용이 7만5천 달러에서 75만 달러를 넘어갈 수 있다고 분석하며, 그 중 데이터 준비에만 전체 예산의 30%에서 50%가 소요된다고 말한다.[3] 규제 산업에서 HIPAA, SOC 2, ISO 42001 등 컴플라이언스 요건을 충족하기 위해 추가되는 비용은 10만에서 60만 달러 수준으로, 기본 구축 비용에 상당한 프리미엄을 붙일 수 있다.[3] 또한 모델 유지·운영 비용은 초기 구축 비용의 연 15%에서 25% 수준으로 발생하며, 예를 들어 40만 달러 규모의 파인튜닝 프로젝트를 수행한 경우 연간 6만에서 10만 달러의 모델 운영비를 부담해야 한다고 분석한다.[3] 이런 자료들은 “전체 LLM 관련 비용에서 모델 추론 비용이 차지하는 비율이 생각보다 낮을 수 있다”는 방향의 논지를 뒷받침한다.

한편, GPU 인프라와 토큰 단가를 분석한 GpuNex의 “AI Inference Economics: The 1,000× Cost Collapse Reshaping GPUs”는 GPT‑4급 모델의 토큰당 비용이 지난 3년간 1,000배 가까이 하락했다는 사실을 보여준다.[11] 2022년 말에는 GPT‑4 수준 모델을 운영하는 데 백만 토큰당 약 20달러가 들었지만, 2026년 초에는 동일 수준 성능을 백만 토큰당 0.40달러 이하로 제공할 수 있게 되었다는 것이다.[11] 이는 하드웨어 개선(세대당 2~3배), 소프트웨어 최적화(연속 배칭, PagedAttention 등으로 2~3배), 모델 아키텍처 효율 향상(MoE로 3~5배), 양자화(2~4배) 등 네 가지 요인이 복합적으로 작용한 결과로 설명된다.[11] 이러한 비용 하락에도 불구하고, Semianalysis의 ChatGPT 비용 모델은 “합리적인 규모에서 모델을 배포할 때 추론 비용이 훈련 비용을 크게 상회한다”고 지적한다.[16] ChatGPT 서비스를 운영하는 데 필요한 HGX A100 서버 수(약 3,617대, GPU 28,936개)를 기반으로, 하루에 약 69만4,444달러의 하드웨어 비용이 발생하며, 쿼리당 비용은 약 0.36센트로 추정된다.[16]

이처럼 각 자료는 서로 다른 관점을 제공한다. Cockroach Labs는 “추론 = TCO의 20%, 비‑추론 = 80%”라는 분해를 제시하며, TechAhead는 전체 LLM 프로젝트에서 데이터 준비·컴플라이언스가 큰 비율을 차지한다고 강조한다.[3][4] Semianalysis와 GpuNex는 추론 자체의 막대한 비용과 그 급격한 하락을 보여주고, Agentic AI 논문은 실행 시간 기준으로 LLM 추론 비중이 71~98%라는 결과를 제시한다.[2][11][16] 중요한 점은, 이들 사이에 “LLM 59%, Search 24%, DB 17%, 비‑LLM 41%” 같은 단일 합의 숫자가 존재하지 않는다는 것이다. 각 자료는 자신이 정의한 “전체 비용” 또는 “전체 시간”을 기준으로 분해를 제시할 뿐, 업계 전체가 공유하는 표준 분해표는 아직 발표된 바 없다.

### 2.3. AI 비용 초과와 거버넌스에 대한 설문조사

C4·C2 주장은 AI 비용 초과와 예산 예측 실패를 강조하는 맥락에서 등장하므로, 해당 주제를 다룬 설문조사를 검토하는 것이 중요하다. DoiT와 Sapio Research가 2026년 초에 발표한 AI 지출 설문조사에 따르면, 설문에 응답한 모든 조직이 이미 AI에 지출을 하고 있으며, 지난 12개월 동안 AI 비용 초과를 경험한 비율은 79%에 달한다.[9] 그럼에도 불구하고, AI ROI를 “중대한 병목 없이” 계산할 수 있다고 응답한 조직은 15%에 불과했다.[9] 이는 대부분의 조직이 AI 비용의 불확실성에 노출되어 있으며, 비용 초과를 경험하고도 이를 체계적으로 측정·관리하지 못하고 있음을 시사한다. 기사에서는 표본 수와 산업별 분포를 상세히 제시하지는 않지만, 설문대상은 주로 미국과 영국에 기반을 둔 중대형 기업 재무 리더들로 구성된 것으로 설명된다.[9]

Mavvrik와 Benchmarkit이 공동으로 작성한 “2026 State of AI Cost Governance Report”는 보다 구체적인 거버넌스 지표를 제공한다.[10] 이 보고서는 2025년에 다양한 산업·매출 규모를 가진 372개 기업을 대상으로 수행한 설문 데이터를 분석하여, AI 인프라 비용 예측 정확도, 비용 할당 능력, 매출총이익(gross margin)에 대한 영향 등을 살핀다.[10] 보고서에 따르면, AI 인프라 예측이 근본적으로 실패하고 있다는 진단이 내려진다. 응답 기업의 80%가 AI 인프라 예측에서 25% 이상 오차를 경험했고, 89%는 AI 관련 예산 예측을 10% 이상 빗나가고 있다고 응답했다.[10] 또한 84%의 기업은 AI 인프라 비용으로 인해 6% 이상의 매출총이익 감소를 경험하고 있으며, 62%는 예기치 못한 AI 비용이 실제 사업 의사결정을 바꾸는 수준의 “빌 쇼크(bill shock)”를 일으켰다고 응답했다.[10] 구체적으로, 40%는 이사회 차원으로의 에스컬레이션, 33%는 긴급 지출 동결, 25%는 AI 프로젝트 지연·취소를 경험한 것으로 보고된다.[10]

이들 설문조사는 특정 기업 한두 곳의 사고 사례가 아니라, 수백 개 기업에서 나타나는 구조적 패턴을 보여준다. 특히 Mavvrik 보고서에서 드러나는 “예산 예측 실패”와 “매출총이익 감소”는 투자자 입장에서 매우 중요한 신호이다.[10] 스타트업 창업자가 투자자에게 “AI 비용 거버넌스가 대부분의 기업에서 실패하고 있다”는 메시지를 전달하고자 할 때, 개발자 개인의 사고 사례(예: 무한 루프 에이전트)보다 이러한 집계 통계를 인용하는 것이 설득력이 높을 수 있다. 다만 이 설문조사들은 비용 급증의 시간 스케일을 “하룻밤” 또는 “2일” 수준으로 특정하지는 않으며, 대체로 “지난 12개월” 또는 “최근 분기” 단위로 초과지출·예측실패를 측정한다.[9][10] 따라서 C4에서처럼 “하룻밤 동안 400% 증가”라는 구체적인 시간·비율 조합을 주장하려면 별도의 사례나 데이터가 필요하다.

## 3. C2 — “AI 원가의 41%는 비‑LLM이다” 주장 분석

### 3.1. 주장 내용과 검증 질문

C2는 슬라이드 [3]의 핵심 숫자로서, “LLM 59%, Search 24%, External DB 17%”라는 분해를 통해 AI 원가(COGS)의 41%가 모델 외 구성요소에 쓰인다는 메시지를 담고 있다. 한국어 요약으로는 “AI 원가의 41%가 모델을 한 번도 거치지 않는다” 또는 “41% of COGS never touches a model”과 같은 표현이 사용된다. 이 숫자는 피치덱에서 “업계 전체에 일반화 가능한 합의 수치”처럼 제시되었으나, 선행 분석에서는 Menlo Ventures의 엔터프라이즈 AI 리포트, LangChain의 State of AI Agents, FinOps Foundation 자료 등을 검토했음에도 해당 분해를 담은 공개 출처를 찾지 못했다고 보고했다.[2][4][12]

본 보고서의 첫 번째 검증 질문은 다음과 같다. “LLM 59%, Search 24%, External DB 17%라는 분해를 포함하는 1차 출처가 실제로 존재하는가?” 두 번째 질문은 “비‑LLM 41%라는 숫자가 Cockroach Labs, TechAhead, Agentic AI 논문 등에서 제시하는 비용·시간 분해와 어느 정도 일치하거나 모순되는가?” 그리고 세 번째 질문은 “이 숫자가 2026년 기준으로 ‘표준 분해’처럼 말할 수 있을 정도로 업계 합의가 되어 있는가?”이다.

### 3.2. 59/24/17 분해를 담은 출처의 부재

우선 제공된 검색 결과들 가운데 “LLM 59%, Search 24%, DB 17%”라는 정확한 분해를 담은 문서는 발견되지 않는다.[1][2][3][4][9][10][12] Menlo Ventures의 “The State of Generative AI in the Enterprise” 리포트는 2025년 기준 기업들이 생성형 AI에 370억 달러를 지출했으며, 2024년 115억 달러에서 3.2배 증가했다는 시장 규모를 제시한다.[12] 또한 애플리케이션 레이어에서 “수평형(horizontal) AI”가 84억 달러로 가장 큰 카테고리이며, 그 중 86%(72억 달러)가 ChatGPT Enterprise, Claude for Work, Microsoft Copilot 등 코파일럿 애플리케이션에 쓰인다고 분석한다.[12] 그러나 이 보고서는 “애플리케이션 레이어에서 어떤 비율이 LLM 추론 vs 검색 vs 데이터베이스 호출에 쓰이는지” 같은 미시적 비용 구조를 분해하지 않는다.

Portkey.ai의 LLM 프라이싱 블로그는 “3,500개 이상의 모델, 1억8천만 달러 이상의 LLM 지출 데이터를 추적했다”고 말하며, 모델 가격 책정의 숨은 패턴을 설명하지만, 역시 비용 구성요소를 구체적으로 분해하지 않는다.[1] Agentic AI 논문은 앞서 살펴보았듯이 실행 시간 기준으로 LLM vs 툴 호출의 비율을 제시할 뿐, 비용 분해에 대해서는 언급하지 않는다.[2] Cockroach Labs 블로그는 “LLM 추론은 TCO의 약 20%, 나머지 80%는 모델 주변 비용”이라는 거시적 분해를 제시하지만, 그 80%를 다시 검색·데이터베이스·모니터링·인프라 등으로 세부 분할하지는 않는다.[4] TechAhead 보고서 역시 LLM 프로젝트 전체 비용에서 데이터 준비가 30~50%, 컴플라이언스가 경우에 따라 10만~60만 달러라는 식의 “프로젝트 비용 내 비율·절대액”을 설명할 뿐, 실시간 추론 원가의 미시구조를 59/24/17 같은 숫자로 나누지 않는다.[3]

요약하면, 우리는 제공된 검색 결과 안에서 C2의 59/24/17 분해를 담은 1차 출처를 찾지 못했다. 이는 두 가지 가능성을 시사한다. 하나는 이 숫자가 특정 회사 내부의 프로덕션 계측 결과로서, 외부에 공개된 적이 없다는 것이다. 다른 하나는 숫자 자체가 임의로 구성되었거나, 여러 서로 다른 출처의 숫자를 혼합한 결과라는 것이다. 어느 쪽이든, 이 숫자를 “공개 조사·벤치마크·벤더 리포트가 제시하는 표준 분해”로 말하는 것은 현재로서는 근거가 없다.

### 3.3. Cockroach Labs와 TechAhead 수치와의 비교

비‑LLM 비용 비중을 논의할 때 종종 인용되는 Cockroach Labs의 “The Bill Arrives” 블로그는 추론 비용의 상대적 비중을 강조하는 대표적인 자료이다.[4] 이 글은 “실제 조직에서 AI 에이전트를 운영할 때, 리더들은 추론 비용만을 보고 비용을 과소평가하는 경향이 있다”고 지적하며, “실제로는 추론이 TCO의 약 20%에 불과하다”고 주장한다.[4] 나머지 80%는 오케스트레이션, 평가·모니터링, 데이터 플랫폼, 인프라·라이센싱 등으로 분해되는데, 특히 데이터 클리닝·전처리가 대부분의 RAG 프로젝트에서 전체 비용의 30~50%를 차지한다는 점을 강조한다.[4] 또한 “RAG Implementation Cost 2026” 자료를 인용해, OpenAI의 text‑embedding‑3‑small을 백만 토큰당 0.02달러, Cohere의 Embed‑4를 백만 토큰당 약 0.12달러로 제시하며, 문서 업데이트 시 재임베딩·재인덱싱 비용을 감안해 월 비용의 20% 정도를 이 용도로 예산 편성해야 한다고 조언한다.[4]

TechAhead 보고서는 다른 각도에서 비슷한 메시지를 전한다. 대부분의 엔터프라이즈 커스텀 LLM 프로젝트에서 데이터 준비가 전체 프로젝트 비용의 30~50%를 차지하며, 컴플라이언스 비용이 규제 산업에서 기본 구축 비용에 10만~60만 달러를 더하는 형태로 나타난다는 것이다.[3] 또한 7B~13B 모델을 단일 A100 GPU로 셀프 호스트하는 경우 24/7 운영 기준으로 월 1,500~5,000달러, 70B 모델을 4~8 GPU로 운영하는 경우 15,000~40,000달러, 대규모 엔터프라이즈 배포(70B+ 고동시성)의 경우 50,000~150,000달러 정도의 추론 인프라 비용을 예시로 든다.[3] 이 과정에서 “연간 모델 유지·운영비는 초기 구축 비용의 15~25% 수준”이라는 규칙도 소개된다.[3] 이런 수치들은 “비‑LLM 비용이 무시할 수 없는 수준”이라는 점을 보여주지만, C2의 41%와 직접적으로 정합성을 가늠하기에는 기준이 다르다. Cockroach Labs는 TCO를 기준으로 추론 20% vs 비‑추론 80%를 제시하고, TechAhead는 프로젝트 구축·운영 전체 비용에서 데이터 준비·컴플라이언스·추론 인프라의 비중을 논하기 때문이다.[3][4]

Agentic AI 논문은 시간 기준으로 LLM 71~98%, 툴 2~29%라는 결과를 제시하여, 비‑LLM 시간이 많아야 29%라는 상한을 보여준다.[2] Cockroach Labs는 비용 기준으로 비‑LLM 비중이 80%까지 올라갈 수 있음을 주장한다.[4] TechAhead는 프로젝트 전체 비용에서 데이터 준비·컴플라이언스·인프라가 상당한 비율을 차지한다는 사실을 보여준다.[3] 이 세 자료를 함께 보면, “비‑LLM 비중은 COGS 경계를 어디에 설정하느냐, 그리고 시간 vs 비용 중 무엇을 기준으로 삼느냐에 따라 크게 달라진다”는 결론을 얻을 수 있다. 따라서 “비‑LLM은 정확히 41%”라는 숫자를 업계 합의치로 말하는 것은 현재 공개 자료들과 조화를 이루지 않는다.

### 3.4. 2026년 기준 안전한 재서술

투자자 Q&A에서 창업자가 C2를 언급하고자 할 때, 가장 안전한 접근은 “자사 계측 결과”인지 여부를 명확히 밝히는 것이다. 제공된 검색 결과로는 59/24/17 분해를 담은 외부 출처가 발견되지 않으므로, 이 숫자가 실제로 특정 프로덕션 워크로드에서 계측된 결과라면 “당사 내부 측정치”로 라벨링해야 한다. 예를 들어 “당사 프로덕션 에이전트 트래픽 기준으로, 최근 3개월 동안 LLM 추론이 COGS의 약 59%, 검색 API가 24%, 외부 데이터베이스 호출이 17%를 차지했다”는 식으로 말하면, 숫자가 공개 합의치가 아니라 특정 계측 환경에 속한 것임을 분명히 할 수 있다. 반대로 이 숫자에 대한 내부 계측이 없다면, 이를 “업계 평균” 또는 “표준 분해”처럼 말하는 것은 피해야 한다.

보다 안전한 재서술은 다음과 같다. “공개 벤치마크와 벤더 보고서를 보면, 에이전트 워크로드에서 LLM 추론 시간이 전체 실행 시간의 71~98%를 차지하는 경우가 많고, 툴 실행 시간은 2~29% 사이에서 워크로드에 따라 크게 변동한다.[2] Cockroach Labs와 TechAhead 같은 벤더는 전체 TCO 기준으로 추론 비용이 약 20%에 불과하며, 나머지 80%는 오케스트레이션, 데이터 준비, 컴플라이언스, 인프라에 쓰인다고 분석한다.[3][4] 즉, AI COGS에서 모델 외 구성요소가 차지하는 비중은 워크로드와 비용 경계 정의에 따라 20%에서 80%까지 매우 넓게 분포하며, 업계가 합의한 단일 ‘59/24/17’ 분해는 아직 존재하지 않는다.” 이 정도 수준의 서술은 제공된 출처들과 정합성을 유지하면서도, “비‑LLM 비용이 크다”는 메시지를 충분히 전달할 수 있다.

이러한 이유로, 본 보고서는 C2의 “LLM 59 / Search 24 / DB 17 = 비‑LLM 41%”라는 숫자 주장을 외부 출처에서는 뒷받침할 수 없다고 판단하여 UNVERIFIABLE로 분류한다. 여기서 “UNVERIFIABLE”은 숫자가 내부 계측 결과일 가능성을 배제하지 않지만, 투자자에게 “업계 합의치”처럼 말하는 것은 위험하다는 의미이다.

## 4. C3 — “무한 루프 에이전트로 11일간 4만7천 달러를 썼다” 사례 검증

### 4.1. Towards AI·dev.to 사건 서술 비교

C3는 슬라이드 [4]의 첫 번째 숫자 카드로, “무한 루프에 빠진 AI 에이전트 시스템이 11일 동안 돌아가면서 4만7천 달러의 비용을 발생시켰다”는 일화에 기반한다. 이 사건에 대한 가장 직접적인 출처는 Teja Kusireddy가 Towards AI에 게시한 글 “We Spent $47,000 Running AI Agents in Production. Here's What Nobody Tells You About A2A and MCP”이다.[5] 제공된 검색 결과에서 이 글의 일부를 보면, “지난해 우리의 AI 에이전트가 11일 동안 무한 루프에 빠졌다. 비용: 47,000달러”라는 문장이 등장한다.[5] 이어지는 서술에서는 첫 주 API 비용이 127달러였고, 이후 주별로 891달러, 6,240달러, 18,400달러로 증가했다고 설명한다.[5] 이 글은 팀 단위(“우리의 팀”, “우리의 에이전트”) 경험을 담고 있으며, 구체적인 회사명이나 인보이스 스크린샷은 포함하지 않는다.[5]

dev.to에 게시된 “The AI Agent That Cost $47000 While Everyone Thought It Was Working”은 같은 사건을 재구성하면서 추가적인 해설을 제공한다.[13] 이 글은 “11일 동안 다중 에이전트 연구 시스템이 프로덕션에서 정확히 설계된 대로 동작하고 있었다. 에이전트들이 서로에게 질문을 던지고, 요청을 처리하며, 메시지를 전달했다. 대시보드는 활동을 보여주고, 레이턴시는 정상으로 보였으며, 에러는 발생하지 않았다. 시스템은 건강해 보였다. 다만 아무런 유용한 일을 하지 않고 있었다”고 서술한다.[13] dev.to 글은 네 주간의 API 비용을 표로 제시하며, 127달러, 891달러, 6,240달러, 18,400달러라는 패턴을 보여준다.[13] 그리고 주석에서 “주당 API 비용은 보고된 에스컬레이션 패턴을 반영한다. 47,000달러라는 총액은 원 사건 보고서에서 분리해서 제시되지 않은 추가 인프라·컴퓨트 비용을 포함한다”고 설명한다.[13]

이 두 글을 함께 보면, 몇 가지 사실이 명확해진다. 첫째, “무한 루프 기간이 11일이었다”는 서술은 Towards AI 글에서 직접 등장한다.[5] dev.to 글은 전체 시스템이 4주 동안 점진적으로 비용을 증가시키는 과정을 설명하며, 11일이라는 숫자를 루프가 발견되지 않은 기간으로 해석한다.[13] 둘째, “4만7천 달러”라는 총 비용 숫자 역시 Towards AI 글의 제목과 본문에서 명시되어 있으며, dev.to 글에서도 “총 비용 47,000달러”로 재인용된다.[5][13] 셋째, 주별 API 비용 합계(25,658달러)는 총액 47,000달러보다 적지만, dev.to 글은 주석에서 “나머지 비용은 인프라·컴퓨트 등 다른 항목에 포함된다”고 명시함으로써 이 불일치를 부분적으로 설명한다.[13] 따라서 “주차별 API 비용만으로는 47,000달러가 나오지 않는다”는 지적은 맞지만, 원 사건 보고서가 총 비용에 API 외 인프라 비용을 포함했음을 감안하면 꼭 “산수가 틀렸다”고 볼 필요는 없다.

### 4.2. 숫자·기간의 정확성과 한계

이 사건의 핵심 숫자, 즉 “11일”과 “47,000달러”는 두 출처 모두에서 반복적으로 등장한다.[5][13] Towards AI 글은 루프 기간과 총 비용을 직설적으로 묘사하고, dev.to 글은 이를 바탕으로 보다 구조적인 “패턴”과 “제도적 교훈”을 풀어낸다.[5][13] 다만 이 숫자들은 모두 사건 당사자의 자기 보고에 기반해 있으며, 외부에서 독립적으로 검증된 인보이스나 클라우드 청구서가 첨부되어 있지 않다. 또한 회사명·벤더명·국가 등 사건의 컨텍스트가 최소한으로만 드러나므로, 투자자가 “어느 클라우드, 어느 AI API에서 발생한 일인지”까지 알고 싶어 한다면, 이 자료만으로는 답하기 어렵다.[5][13]

그럼에도 불구하고, 이 사건은 AI 에이전트 시스템의 위험성을 보여주는 대표적인 사례로 널리 인용되고 있다. dev.to 글 자체가 “이 사건은 A2A(AI‑to‑AI) 시스템이 제대로 작동하고 있다고 믿는 동안 어떤 일이 벌어질 수 있는지를 보여주는 패턴”이라고 명시하며, 무한 루프에 빠진 두 에이전트가 서로에게 확인 요청과 검증 지시를 무한히 주고받는 동안, 모니터링 대시보드에는 정상적인 활동과 레이턴시가 표시되었다고 설명한다.[13] 위험은 “에러가 없기 때문에” 감지되지 않았고, 최종적으로는 청구서를 보고서야 이상을 발견했다는 것이다.[13] 이 패턴은 API 키 탈취나 LLMjacking 공격보다 “더 교활한” 위험으로 묘사되며, 비용 통제와 실행 전 차단의 필요성을 강조하는 논거로 사용된다.[6][8][13]

투자자 Q&A에서 이 사건을 언급할 때, 가장 큰 위험은 숫자를 과도하게 일반화하는 것이다. 예를 들어 “LLM 에이전트가 무한 루프에 빠지면 11일에 47,000달러가 든다”는 식으로 말하면, 특정 사건의 맥락을 제거한 채 전체 시장을 과장하는 효과를 낳을 수 있다. 보다 안전한 재서술은 “한 팀이 프로덕션에서 다중 에이전트 시스템을 운영했는데, 두 에이전트가 서로에게 확인·검증 메시지를 무한히 주고받는 루프에 빠지면서, 4주간 API와 인프라 비용 합계로 47,000달러가 청구된 사례가 보고된 바 있다.[5][13] 이 사건에서 루프가 발견되지 않은 기간은 11일이었고, 대시보드에는 정상적인 활동으로 표시되어 팀이 청구서를 보기 전까지 문제를 알지 못했다” 정도이다. 이렇게 말하면, 숫자가 특정 사례에 속한다는 점을 명확히 하면서도 교훈을 전달할 수 있다.

본 보고서는 이 사건이 실제로 보고된 바 있으며, 11일·47,000달러라는 숫자가 출처에서 반복적으로 나타난다는 점을 감안해 C3를 CONFIRMED로 분류한다. 다만 CONFIRMED는 “사건이 자기 보고에 기반해 존재한다”는 의미이지, “모든 에이전트 시스템이 유사 상황에서 정확히 동일한 비용을 발생시킨다”는 의미는 아니다.

### 4.3. Gemini API 키 탈취 및 LLMjacking 사례와의 비교

C3를 검증하는 과정에서, 선행 분석이 제안한 대체 사례인 “Gemini API 키 탈취로 2일간 82,314달러가 청구된 사건”과 Sysdig가 보고한 “LLMjacking 공격으로 하루 최대 46,080달러 손실 가능성”도 함께 검토했다.[6][8] Tom's Hardware 기사에 따르면, 한 Google Gemini 사용자가 레딧에 “충격과 공포 상태”라고 토로하면서, 최근 청구서를 받은 뒤 자신의 소프트웨어 개발 사업이 파산 위기에 처했다고 호소했다.[6] 이 사용자는 평소 Gemini AI 서비스에 월 180달러 정도를 지출했으나, 최근 두 달 가운데 특정 48시간 동안 계정이 82,314.44달러의 비용을 발생시켰다는 것이다.[6] 레딧 사용자는 누군가 자신의 API 키를 탈취해 Gemini 3 Pro Images 및 Texts 모델을 대량 호출했다고 주장하며, 키를 삭제하고 Gemini API를 비활성화하고, IAM을 잠그고 2FA를 활성화했지만 이미 비용은 발생한 뒤였다고 설명한다.[6] 기사에 따르면, 초기에는 Google 담당자가 해당 비용이 그대로 청구될 가능성이 높다고 응답해 논란을 일으켰다.[6]

Sysdig Threat Research Team은 또 다른 유형의 공격인 “LLMjacking”을 보고했다.[8] 이 공격은 탈취된 클라우드 자격 증명을 이용해 Anthropic Claude 2.x 모델을 AWS Bedrock을 통해 호출하는 방식으로, 피해자가 눈치채지 못하는 사이 막대한 LLM 추론 비용을 발생시킬 수 있다.[8] Sysdig는 Claude 2.x에 대한 AWS Bedrock 초기가용 쿼터를 기준으로 최악의 시나리오를 계산했다. 입력 토큰 천 개당 비용은 0.008달러, 출력 토큰 천 개당 비용은 0.024달러이며, 평균 비용을 천 토큰당 0.016달러로 설정한다.[8] AWS Bedrock은 분당 최대 50만 입력·출력 토큰을 허용하므로, 이를 기준으로 60분·24시간·4개 리전을 곱하면 하루 비용은 (500,000/1,000 × 0.016) × 60 × 24 × 4 = 46,080달러가 된다.[8] Sysdig는 이러한 계산을 통해 “탈취된 자격 증명이 한 기업의 Claude 사용 쿼터를 여러 리전에 걸쳐 최대치까지 소진하면, 피해자에게 하루 46,000달러 이상의 비용을 안길 수 있다”고 결론내린다.[8]

Gemini 사건과 LLMjacking 사례는 Teja Kusireddy의 무한 루프 사례보다 출처의 신뢰도가 비교적 높다. Tom's Hardware는 피해자의 레딧 글을 인용하면서 끊임없이 업데이트되는 스크린샷과 Google의 초기 대응을 함께 보도하고, Sysdig는 AWS Bedrock·Claude 가격표에 기반해 최악의 시나리오 비용을 세부적으로 계산한다.[6][8] 두 사건 모두 “키 탈취 또는 자격 증명 탈취 → 공격자가 LLM 서비스에 대량 요청 → 피해자에게 막대한 비용 청구”라는 패턴을 공유한다. 투자자 Q&A에서 “키 유출로 짧은 시간에 비용이 폭증한 사례”를 언급하고자 한다면, Gemini 82,314달러 사건과 LLMjacking 46,080달러/일 사례를 함께 제시하는 것이 Teja Kusireddy의 자기 보고 사례보다 더 견고한 근거를 제공할 것이다.[6][8]

그러나 C3의 본질은 “실행 전 차단·비용 한도 없이 프로덕션 에이전트를 운영하면, 무한 루프나 이상 행동으로 인해 수만 달러의 비용 폭탄이 터질 수 있다”는 것이다. 이 메시지를 전달하는 데에는 Teja Kusireddy의 사례도 충분한 역할을 한다. 따라서 C3는 “대표적 자기 보고 사례”로 CONFIRMED로 유지하되, 투자자와의 대화에서 보다 보수적인 서술을 사용하고, 필요하다면 Gemini·LLMjacking 사례를 병행 인용하는 것이 안전하다.

### 4.4. 안전한 재서술

위의 분석을 바탕으로, 투자자 Q&A에서 사용할 수 있는 안전한 재서술은 다음과 같이 요약할 수 있다. “2025년에는 한 팀이 프로덕션에서 다중 AI 에이전트 시스템을 운영하다가, 두 에이전트가 서로에게 확인과 검증 메시지를 무한히 주고받는 루프에 빠지면서 네 주 동안 API·인프라 비용 합계로 47,000달러가 청구된 사례가 자기 보고로 공유된 바 있습니다.[5][13] 루프가 발견되지 않은 기간은 11일이었고, 모니터링 대시보드에는 모든 것이 정상처럼 보였기 때문에 팀은 청구서를 보기 전까지 문제를 알지 못했습니다.[5][13] 비슷한 시기에, Gemini API 키 탈취로 이틀 사이에 82,314달러가 청구된 사건과, AWS Bedrock의 Claude 서비스를 겨냥한 LLMjacking 공격으로 하루 46,000달러 이상의 비용이 발생할 수 있다는 시나리오도 보고되었습니다.[6][8] 이런 사례들은 AI 시스템에 실행 전 지출 한도와 이상 징후 차단 장치가 없을 경우, 짧은 시간에 수만 달러 규모의 비용 폭탄이 터질 수 있다는 점을 잘 보여줍니다.”

이 재서술은 각 사건의 숫자·기간·출처를 정확히 반영하면서도, 특정 사건의 숫자를 전체 시장에 일반화하지 않는다. 따라서 본 보고서의 C3 판정은 CONFIRMED이며, Real Number는 사건 보고에 나온 대략적인 총 비용 47,000달러로 유지하되, API 비용과 인프라 비용이 합산된 숫자라는 점을 명시하는 것이 바람직하다.[5][13]

## 5. C4 — “하룻밤 사이 API 비용이 400% 급증했다” 주장 분석

### 5.1. 문서화된 “하루·하룻밤” 단위 비용 급증 사례 탐색

C4는 슬라이드 [4]의 두 번째 숫자 카드로, “하룻밤 동안 API 비용이 400% 급증했다”는 일화 또는 일반화를 담고 있다. 선행 분석은 이 숫자와 시간 스케일을 만족하는 문서화된 사례를 찾지 못했다고 보고하며, 대신 6개월 동안 AI 지출이 500% 증가한 Boston 스타트업 사례와 연간 AI 지출 증가율을 다룬 Zylo·CloudZero 보고서를 언급했다.[17] 본 보고서에서는 제공된 검색 결과 안에서 “하루 또는 하룻밤 단위로 API 비용이 400% 이상 증가했다”고 명시한 출처가 있는지 다시 탐색했다.

Gemini API 키 탈취 사건은 “48시간 동안 82,314달러가 청구되었다”는 극단적 급증 사례를 제공하지만, 기사에서는 피해자의 기존 월 지출(180달러)을 기준으로 상대적 증가율을 계산하지 않는다.[6] 단순히 월평균 180달러를 30일로 나누면 하루 6달러 수준이지만, 이런 환산은 기사 본문에서 수행되지 않으며, 따라서 “하루/하룻밤에 몇 퍼센트 증가했다”는 표현으로 직접 인용하기에는 조심스럽다.[6] Sysdig의 LLMjacking 계산은 최악의 시나리오에서 하루 46,080달러 비용이 발생할 수 있다고 제시하지만, 이는 “노멀 상태 대비 증가율”이 아니라 절대값이다.[8] 따라서 “어제 대비 오늘 400% 증가했다”는 식의 상대적 증가율을 담고 있지는 않다.

Washington Examiner 기사에서 Via라는 Boston 기반 스타트업의 CTO가 “AI 지출이 6개월 동안 500% 증가했다”고 언급하는 사례는 존재한다.[17] 이 기사에 따르면, 스타트업은 AI 인프라 지출이 6개월 사이에 다섯 배로 늘어나면서 재정적 압박을 겪고 있으며, CTO는 “AI가 워크플로에 깊이 들어오면, 지출이 조용히 배경에서 증가한다. 적극적으로 관리하지 않으면 5,000달러 또는 10,000달러짜리 청구서에 빠르게 도달할 수 있다”고 말한다.[17] 그러나 이 사례 역시 6개월 단위 지출 증가율을 묘사할 뿐, 하루 또는 하룻밤 단위 400% 급증을 언급하지 않는다.

DoiT·Mavvrik 설문조사는 비용 초과 빈도와 예산 예측 실패율을 보여줄 뿐, 특정 시간 스케일에서의 지출 증가율을 제공하지 않는다.[9][10] 예를 들어 DoiT 설문에서는 “응답 기업의 79%가 지난 12개월 동안 AI 비용 초과를 경험했다”고 보고하며, Mavvrik 보고서는 “응답 기업의 89%가 AI 인프라 예측을 10% 이상 빗나가고 있다”고 설명한다.[9][10] 이 숫자들은 비용 통제 실패의 광범위한 패턴을 보여주지만, “하룻밤 400% 급증”이라는 구체적 표현을 뒷받침하지는 않는다.

결론적으로, 제공된 검색 결과 안에서는 “하룻밤 또는 하루 동안 API 지출이 400% 증가했다”는 문구를 포함한 문서화된 사례가 발견되지 않는다.[6][8][9][10][17] Gemini·LLMjacking 사건은 극단적 폭증을 보여주지만, 상대적 증가율을 하루 단위로 명시하지 않으며, Via 스타트업 사례는 6개월 단위 500% 증가를 다룰 뿐이다.[6][8][17] 따라서 C4의 “하룻밤 400% 급증”이라는 주장은 외부 출처로는 UNVERIFIABLE한 상태로 보아야 한다.

### 5.2. 설문조사를 통한 구조적 비용 초과의 묘사

그렇다고 해서 “비용 급증 위험이 없다”는 의미는 아니다. 앞서 살펴본 DoiT·Mavvrik 설문조사는 조직들이 AI 비용을 얼마나 자주 초과하고 있는지, 그리고 그 결과가 얼마나 심각한지 보여준다.[9][10] DoiT 설문에서 79%의 조직이 지난 12개월 동안 AI 비용 초과를 경험했고, Mavvrik 보고서에서는 62%의 조직이 예기치 못한 AI 비용으로 인해 사업 의사결정을 변경했다고 응답했다.[9][10] Mavvrik 보고서의 구체 수치를 보면, 40%의 응답 기업이 AI 비용 문제를 이사회 차원으로 에스컬레이션했고, 33%는 긴급 지출 동결 조치를 취했으며, 25%는 AI 프로젝트를 지연하거나 취소했다.[10] 이러한 수치는 단일 개발자의 사고 사례보다, 투자자에게 더 설득력 있는 “리스크의 구조적 측면”을 보여준다.

또한 Mavvrik 보고서는 “Forecasting is fundamentally broken”이라는 표현을 사용하면서, 80%의 기업이 AI 인프라 예측에서 25% 이상의 오차를 경험하고 있다고 설명한다.[10] 이는 조직들이 AI 지출을 예측할 수 있는 능력 자체가 부족하다는 의미이며, 예상치 못한 급증이 발생할 경우 이를 사전에 감지하거나 완충할 여력이 부족함을 시사한다. DoiT 설문에서 “AI ROI를 병목 없이 계산할 수 있다”고 답한 기업이 15%에 불과한 것도 같은 맥락이다.[9] 이처럼 구조적 거버넌스 실패가 널리 퍼져 있는 상황에서, “하룻밤 400% 급증”이라는 구체 사례 없이도 투자자에게 비용 급증 위험을 설명할 수 있다.

Washington Examiner 기사에서 Via 스타트업 CTO가 언급한 “6개월 500% 증가” 사례는, 시간 스케일을 고려하면 C4의 메시지를 보다 현실적으로 재구성할 수 있는 소재를 제공한다.[17] CTO는 “AI가 워크플로에 내장되면, 지출이 조용히 증가한다. 적극적으로 모니터링하지 않으면 5,000달러 또는 10,000달러 청구서에 빠르게 도달할 수 있다”고 말한다.[17] 이는 “하룻밤 급증”처럼 극단적인 표현은 아니지만, “비용이 배경에서 조용히 성장해 어느 순간 큰 청구서로 나타난다”는 패턴을 잘 포착한다. Dev.to·Towards AI 사건에서 무한 루프 에이전트 비용이 4주 동안 서서히 증가해 네 번째 주에 18,400달러까지 도달한 패턴과도 유사하다.[5][13]

### 5.3. 안전한 재서술과 판정

이러한 이유로, C4의 “하룻밤 400% 급증”을 그대로 유지하는 것은 위험하다. 제공된 검색 결과 안에서 동일 시간·비율을 갖는 문서화된 사례를 찾지 못했으므로, 이 숫자는 UNVERIFIABLE하다. 투자자 Q&A에서는 보다 견고한 설문조사·사례를 기반으로 메시지를 재구성하는 것이 안전하다. 예를 들어 다음과 같은 재서술이 가능하다. “단일 개발자 사례 대신, 우리는 수백 개 기업의 설문 데이터를 보는 편을 선호합니다. DoiT 설문에 따르면 지난 12개월 동안 AI 비용 초과를 경험한 기업이 79%에 달하고, Mavvrik 보고서는 372개 기업 중 89%가 AI 예산 예측을 10% 이상 빗나가고 있다고 답했습니다.[9][10] 62%는 예기치 못한 AI 비용 때문에 실제 사업 의사결정을 바꾸었고, 40%는 이사회 에스컬레이션, 33%는 긴급 지출 동결, 25%는 AI 프로젝트 지연이나 취소를 경험했습니다.[10] 한 Boston 스타트업의 경우, 6개월 사이 AI 인프라 지출이 500% 증가하면서 재정 압박을 겪었다고 보고했습니다.[17] 즉, 숫자를 어떻게 표현하든, 오늘날 기업들이 AI 비용 급증과 예산 예측 실패라는 구조적 리스크에 직면해 있다는 점은 명확합니다.”

이 재서술은 “하룻밤 400%”라는 구체 숫자를 사용하지 않으면서도 구조적 위험을 설득력 있게 전달한다. 따라서 본 보고서는 C4를 UNVERIFIABLE로 분류하며, Real Number에는 “하룻밤 400%”라는 숫자가 외부 출처에서 확인되지 않는다고 명시하는 것이 적절하다고 본다.

## 6. C9a — “Langfuse·Helicone은 추적만 하고 실행 전 차단을 할 수 없다” 주장 분석

### 6.1. Helicone·Langfuse 기능에 대한 검색 결과 한계

C9a는 슬라이드 [7]의 경쟁 포지셔닝에서, Langfuse와 Helicone을 “추적만 하는 관측성 도구”로 분류하며, “이들은 실행 전 차단(pre‑execution blocking)을 제공하지 않는다”는 메시지를 암묵적으로 담고 있다. 그러나 제공된 검색 결과 안에는 Langfuse나 Helicone의 공식 문서가 포함되어 있지 않다.[14][15] 따라서 이 두 벤더의 최신 기능 목록을 직접 확인하는 것은 불가능하다. 선행 분석은 Helicone 공식 문서에서 `Helicone-RateLimit-Policy` 헤더가 `cents` 단위와 `user` 세그먼트를 지원하며, “사용자당 시간당 5달러 지출 상한”을 예시로 들고, 상한 초과 시 429 에러를 반환하여 제공자 호출 전에 요청을 차단한다고 주장했다. 그러나 이 정보는 제공된 검색 결과 안에 포함되어 있지 않으므로, 본 보고서에서는 이를 출처로 사용할 수 없다.

Langfuse에 대해서도 비슷한 제약이 있다. 선행 분석은 Langfuse 블로그에서 “Langfuse is not an LLM proxy... observes from the sidelines”라는 구절을 인용하며, Langfuse가 자체적으로 프록시 기능을 제공하지 않고, LiteLLM 같은 외부 프록시를 권장한다고 설명했다. 이 역시 제공된 검색 결과에는 포함되어 있지 않다. 따라서 본 보고서는 Langfuse·Helicone의 구체적인 기능 목록과 프록시·차단 기능 여부를 직접 판정할 수 없다. 이런 상황에서는 특정 벤더 기능에 대한 “틀렸다/맞다” 판정을 내리기보다는, 제공된 결과 안에서 확인 가능한 다른 게이트웨이 벤더의 기능을 통해 C9a 주장의 “시장 전체에 대한 일반화”가 얼마나 현재를 반영하는지를 평가하는 것이 합리적이다.

### 6.2. Cloudflare AI Gateway와 LangSmith LLM Gateway의 실행 전 차단 기능

제공된 검색 결과에는 Cloudflare AI Gateway와 LangSmith LLM Gateway에 대한 공식 문서·블로그가 포함되어 있다.[14][15] Cloudflare AI Gateway 문서는 “Limits” 섹션에서 지출·요청 한도에 대한 정책을 설명하며, Cloudflare가 관리하는 자격 증명(Cloudflare‑managed credentials)을 사용하는 Unified Billing 모드에서 특정 요율 제한(rate limit)이 적용된다고 밝힌다.[14] 문서에 따르면, 이 한도를 초과하면 AI Gateway는 429 에러를 반환하며, 이는 “요청을 거부한다”는 HTTP 의미를 가진 상태 코드이다.[14] 특히 이 한도는 BYOK(Bring Your Own Keys) 모드에서 사용하는 요청에는 적용되지 않는다고 명시하여, Cloudflare가 관리하는 자격 증명에 대해서만 선제적 차단을 수행한다는 점을 분명히 한다.[14]

LangSmith LLM Gateway 블로그는 보다 직접적으로 실행 전 차단을 강조한다.[15] 이 블로그는 “LLM Gateway gives teams one place to enforce runtime controls across agents, models, and providers, helping them consistently govern model usage while avoiding vendor lock‑in”이라고 소개하며, “Control cost and reliability at runtime — set spend and rate limits, track usage, and configure model fallbacks across any model, provider, or host”라는 메시지를 전한다.[15] 특히 “Avoid cost overruns: LLM Gateway lets you monitor and control LLM spend for internal and external users before it becomes a problem. You can set time‑bound caps and track spend at four levels: organization, workspace, API key, user”라고 설명한다.[15] 캡이 도달했을 때 LLM Gateway는 402 응답 코드로 요청을 차단하고, 에이전트에게 “지출 한도에 도달했다”는 명확한 오류 메시지를 전달한다.[15] 이는 Cloudflare AI Gateway와 유사하게, upstream LLM 제공자까지 요청이 전달되기 전에 게이트웨이 레이어에서 실행을 중단하는 메커니즘이다.[14][15]

이 두 문서는 2026년 기준으로 실행 전 차단 기능이 이미 게이트웨이 기본 기능의 일부가 되었음을 보여준다. Cloudflare와 LangSmith는 모두 비용·요청 한도, 사용자·워크스페이스·조직 수준 정책, 그리고 초과 시 4xx 응답을 통해 요청을 차단하는 기능을 공개적으로 제공하고 있다.[14][15] 따라서 “실행 전 차단은 아무도 하지 않는다”는 식의 시장 묘사는 더 이상 사실이 아니다. 오히려 “실행 전 차단은 이미 여러 게이트웨이가 제공하는 기본 기능이며, 남은 차별화 포인트는 차단의 정확도와 비용 할당 단위”라는 식으로 메시지를 재구성하는 것이 2026년 현실에 더 가깝다.

### 6.3. C9a의 일반화 부분에 대한 판정

C9a는 Langfuse·Helicone을 언급하면서, 암묵적으로 “관측성 툴은 추적만 하고 실행 전 차단을 제공하지 않는다”는 일반화를 포함한다. 제공된 검색 결과 안에서 Langfuse·Helicone의 기능을 직접 확인할 수는 없지만, Cloudflare AI Gateway와 LangSmith LLM Gateway가 이미 실행 전 차단을 제공하는 상황에서는 “관측성 툴·게이트웨이 전체에 대한 일반화”로서 이 주장은 OUTDATED하다.[14][15] 특히 LangSmith LLM Gateway는 LangChain 생태계에서 관측성·평가 기능을 제공하는 LangSmith 플랫폼이 런타임 차단으로 확장된 사례로, “관측성 벤더가 실행 전 차단으로 넘어오지 않았다”는 메시지를 직접적으로 반박한다.[15]

따라서 본 보고서는 Langfuse·Helicone 자체에 대한 기능 판정은 UNVERIFIABLE로 유지하되, C9a가 담고 있는 “실행 전 차단은 아무도 하지 않는다”는 시장 일반화는 OUTDATED로 분류한다. 투자자 Q&A에서 이 주제를 언급할 때에는, “Cloudflare AI Gateway와 LangSmith LLM Gateway 같은 대표적 게이트웨이가 이미 지출·요청 한도를 런타임에서 적용하고, 초과 시 4xx 응답으로 요청을 차단하는 기능을 제공한다”는 점을 명시해야 한다.[14][15] 이를 바탕으로 “우리 제품의 차별화 포인트는 동시성 환경에서의 비용 집계 정확도와, 예산을 API 키가 아니라 고객·팀·비즈니스 단위로 정의하는 능력에 있다”는 방향으로 서사를 재구성하는 것이 바람직하다.

### 6.4. 안전한 재서술

C9a에 대한 안전한 재서술은 다음과 같이 정리할 수 있다. “2026년 기준으로, Cloudflare AI Gateway와 LangSmith LLM Gateway 같은 대표적인 AI 게이트웨이는 이미 런타임에서 지출·요청 한도를 적용하고, 한도를 초과하는 요청을 4xx 응답으로 차단하는 기능을 제공하고 있습니다.[14][15] 즉, 실행 전 차단은 더 이상 누구도 하지 않는 기능이 아니라, 여러 벤더가 지원하는 기본기입니다. Helicone·Langfuse의 최신 기능 범위는 이 보고서에서 제공된 검색 결과로는 확인할 수 없지만, 그 외 생태계에서는 실행 전 차단이 이미 커머디티화되고 있습니다. 우리가 주장할 수 있는 차별화 포인트는 비용 차단의 정확도, 특히 동시성 환경에서 한도를 정확히 맞춰 끊어내는 능력과, 예산을 API 키가 아니라 고객·팀·비즈니스 객체 단위로 정의하는 능력이라고 보는 편이 안전합니다.”

이 재서술은 제공된 자료 안에서 확실히 검증할 수 있는 사실에 기반해 시장 현실을 묘사하며, 특정 벤더 기능에 대한 추측을 피한다.[14][15] 따라서 C9a는 시장 일반화 측면에서 OUTDATED로, Langfuse·Helicone 기능 측면에서는 UNVERIFIABLE로 보는 것이 균형 잡힌 판단이다.

## 7. C10 — “SatGate는 프리론칭 상태다” 주장 분석 및 경쟁 구도

### 7.1. SatGate·Revenium 관련 출처 부재

C10은 슬라이드 [7]에서 SatGate를 “프리론칭” 상태로 묘사하며, 경쟁사로서의 위협 수준을 상대적으로 낮게 평가하는 메시지를 담고 있다. 선행 분석은 satgate.io 웹사이트를 검토한 결과, SatGate가 이미 “Agent Authority & Accountability Layer”라는 문구와 함께 “budgets and scope enforced before execution”과 서명된 Evidence Pack, MCP Gateway 배포 모드, 라이브 대시보드 등을 공개하고 있으며, “Start Free” 가입 버튼까지 있는 가동 중 제품임을 확인했다고 주장했다. 또한 Revenium Guardrails가 2026년 8월 3일에 “Guardrails for Real‑Time AI Spend and Model Use Enforcement”라는 제품을 출시했다고 언급했다.

그러나 제공된 검색 결과에는 satgate.io나 Revenium 관련 공식 문서·보도자료가 포함되어 있지 않다.[1][2][3][4][6][8][9][10][14][15][16][17][18] 따라서 본 보고서는 SatGate가 현재 어떤 제품 단계를 밟고 있는지, Revenium Guardrails가 실제로 어떤 기능을 제공하며 언제 출시되었는지를 직접 검증할 수 없다. “최초 출시일이 2026년 8월 3일이다”나 “현재 라이브다” 같은 구체적인 날짜·상태를 언급하면, 제공된 검색 결과를 넘어서 새로운 URL·발행일·제목을 만들어내는 셈이 되므로 이 보고서의 원칙에 어긋난다.

### 7.2. 실행 전 예산 차단을 제공하는 다른 경쟁자들

SatGate·Revenium에 대한 직접적인 출처는 없지만, 제공된 검색 결과에서 확인할 수 있는 경쟁자들은 존재한다. 앞서 언급한 Cloudflare AI Gateway와 LangSmith LLM Gateway는 실행 전 차단을 제공하며, 예산·요청 한도를 조직·워크스페이스·API 키·사용자 단위로 정의할 수 있다.[14][15] Cloudflare AI Gateway 문서는 Unified Billing 모드에서 Cloudflare가 관리하는 자격 증명에 대한 요율 제한을 적용하며, 한도가 초과되면 429 에러를 반환한다고 설명한다.[14] 이는 “지출 한도”뿐만 아니라 “요청 수” 같은 리소스 한도에도 적용될 수 있으며, 사용자 ID·팀·애플리케이션 단위로 rate limit를 설정할 수 있음을 시사한다.[14] LangSmith LLM Gateway 블로그는 시간 제한이 있는 spend caps를 조직·워크스페이스·API 키·사용자 단위로 설정하고, caps에 도달하면 402 응답으로 요청을 차단하는 메커니즘을 상세히 설명한다.[15] 이는 다중 에이전트·다중 고객 환경에서 “각 고객 또는 프로젝트별 예산 한도”를 런타임에서 enforce하는 기능으로 볼 수 있다.

Portkey.ai의 LLM pricing 블로그는 비용 구조 분석에 집중하지만, 플랫폼 자체는 LLM 지출 데이터를 수집·분석·최적화하는 기능을 제공하는 것으로 알려져 있다.[1] 제공된 검색 결과에서는 Portkey가 실행 전 차단 기능을 제공하는지 여부를 직접 언급하지 않지만, “우리는 3,500개 이상의 모델에 대한 1억8천만 달러 LLM 지출을 추적해 왔다”고 말하는 부분은 비용 관측·최적화 도구로서의 역할을 보여준다.[1] Cockroach Labs 블로그는 자체 데이터 플랫폼·오케스트레이션 레이어를 통해 Agentic AI 비용을 관리하는 방식을 설명하지만, 실행 전 차단을 직접 제공하는지 여부는 문서에서 명시되어 있지 않다.[4]

이런 자료들을 종합하면, 2026년 기준으로 “실행 전 예산 차단”과 “고객·팀 단위 지출 한도 관리”를 제공하는 벤더들은 이미 여러 곳에 존재한다는 점을 알 수 있다.[14][15] 따라서 SatGate가 유일하거나 가장 앞선 경쟁자라는 식의 묘사는 지나치게 단순화된 것이며, Cloudflare·LangSmith 같은 대형 벤더들의 역할을 함께 고려해야 한다. 투자자 Q&A에서 경쟁 구도를 설명할 때에는 SatGate·Helicone·Langfuse뿐 아니라, Cloudflare AI Gateway와 LangSmith LLM Gateway를 포함해 “실행 전 차단을 제공하는 게이트웨이” 전체를 조망하는 것이 중요하다.[14][15]

### 7.3. C10의 판정과 안전한 재서술

제공된 검색 결과 안에서는 SatGate에 대한 직접적인 출처가 없으므로, C10의 “SatGate는 프리론칭 상태다”라는 묘사는 UNVERIFIABLE하다. 투자자 앞에서 특정 스타트업의 제품 단계를 단정적으로 말하려면, 해당 스타트업의 공식 웹사이트·보도자료·투자 리포트 등에서 명시적인 근거를 찾아야 하는데, 본 보고서의 범위 내에서는 그러한 근거가 제공되지 않는다. 따라서 “SatGate는 아직 프리론칭이라 큰 위협이 아니다”라는 식의 서술은 피하는 것이 좋다.

보다 안전한 재서술은 다음과 같다. “SatGate나 Revenium 같은 신생 벤더에 대한 최신 정보는 이 보고서에서 제공된 검색 결과로는 확인할 수 없지만, Cloudflare AI Gateway와 LangSmith LLM Gateway 같은 기존 대형 벤더들이 이미 실행 전 차단과 비용·요청 한도 기능을 제공하고 있다는 점은 분명합니다.[14][15] 따라서 경쟁을 설명할 때에는 특정 스타트업의 제품 단계에만 초점을 맞추기보다, ‘실행 전 예산·요청 차단’이 커머디티화되는 흐름과, 우리가 그 위에서 어떤 차별화된 회계·정책 레이어를 제공하는지를 강조하는 편이 안전합니다.”

이 재서술은 SatGate의 상태를 추측하지 않으면서도, 경쟁 구도의 본질적 측면을 투자자에게 전달한다. 따라서 본 보고서는 C10을 UNVERIFIABLE로 분류한다.

## 8. 결론 및 투자자 Q&A용 안전 재서술 정리

### 8.1. 다섯 주장에 대한 종합 판정

앞선 섹션들을 종합하면, 검증 대상 다섯 주장(C2, C3, C4, C9a, C10)에 대한 판정은 다음과 같이 요약할 수 있다.

첫째, C2의 “LLM 59 / Search 24 / External DB 17 = 비‑LLM 41%”라는 비용 분해는 제공된 검색 결과 안에서 외부 출처를 찾지 못했다.[1][2][3][4][9][10][12] Agentic AI 논문은 실행 시간 기준으로 LLM 71~98%, 툴 2~29%라는 결과를 제시하고, Cockroach Labs·TechAhead 보고서는 각각 TCO 기준 추론 20% vs 비‑추론 80%, 프로젝트 구축·운영 비용에서 데이터 준비·컴플라이언스 비중이라는 관점을 제공한다.[2][3][4] 그러나 어느 자료도 “59/24/17” 또는 “비‑LLM 41%”라는 숫자를 제시하지 않는다. 따라서 C2는 외부 출처 기준으로 UNVERIFIABLE이며, 이 숫자가 내부 계측 결과라면 “자사 측정치”로 명시한 뒤 사용하는 것이 유일한 안전한 방법이다.

둘째, C3의 “무한 루프 에이전트로 11일간 47,000달러를 썼다”는 주장은 Teja Kusireddy의 Towards AI 글과 dev.to 재구성 글에서 반복적으로 등장하는 자기 보고 사례로서 CONFIRMED다.[5][13] 주별 API 비용 합계(25,658달러)는 총액과 일치하지 않지만, dev.to 글은 “나머지 비용은 인프라·컴퓨트 비용”이라고 설명함으로써 이 불일치를 부분적으로 보완한다.[13] 이 사건은 “에러 없이 정상처럼 보이는 무한 루프 에이전트가 몇 주에 걸쳐 수만 달러의 비용을 발생시킨다”는 위험 패턴을 보여주는 대표 사례이며, 투자자 Q&A에서 이를 언급하는 것은 정당하다. 다만 보다 견고한 근거를 위해 Gemini 82,314달러 사건과 Sysdig LLMjacking 계산도 함께 인용하는 것이 바람직하다.[6][8]

셋째, C4의 “하룻밤 API 비용 400% 급증”이라는 구체 숫자·시간 조합은 제공된 결과 안에서 문서화된 사례를 찾지 못했으므로 UNVERIFIABLE다.[6][8][9][10][17] 대신 DoiT·Mavvrik 설문조사가 “지난 12개월 AI 비용 초과 경험 79%, 예산 예측 실패 89%, 이사회 에스컬레이션 40%, AI 프로젝트 지연·취소 25%”라는 구조적 리스크를 보여주고, Via 스타트업 CTO 사례가 “6개월 500% 증가”라는 장기적 비용 급증을 보고한다.[9][10][17] 따라서 비용 급증 위험을 설명할 때에는 구체적인 숫자를 완화하고, 설문조사·사례 기반 구조적 메시지를 사용하는 것이 안전하다.

넷째, C9a는 Langfuse·Helicone을 언급하면서 “관측성 도구는 추적만 하고 실행 전 차단을 제공하지 않는다”는 시장 일반화를 담고 있다. Langfuse·Helicone의 구체 기능은 제공된 검색 결과 안에서 확인할 수 없어 UNVERIFIABLE지만, Cloudflare AI Gateway와 LangSmith LLM Gateway가 이미 4xx 응답을 통해 실행 전 지출·요청 한도를 enforce하는 기능을 제공한다는 점을 감안하면, 시장 일반화 부분은 OUTDATED로 볼 수 있다.[14][15] 따라서 “실행 전 차단은 누구도 하지 않는다”는 메시지는 2026년 기준으로 유지할 수 없다.

다섯째, C10의 “SatGate는 프리론칭 상태다”라는 묘사는 SatGate 관련 공식 출처가 제공된 검색 결과 안에 없으므로 UNVERIFIABLE하다. SatGate·Revenium과 같은 신생 벤더의 제품 상태를 단정하기보다는, Cloudflare·LangSmith 같은 대형 벤더가 이미 실행 전 차단을 제공하고 있다는 사실을 중심으로 경쟁 구도를 설명하는 것이 안전하다.[14][15]

### 8.3. 전략적 함의

이 팩트체크가 창업자에게 주는 전략적 함의는 두 가지로 요약할 수 있다. 첫째, 숫자는 내부 계측과 외부 출처를 명확히 구분해서 사용해야 한다. “LLM 59 / Search 24 / DB 17”처럼 업계 합의치로 보일 수 있는 숫자는 외부 출처에서 확인되지 않으므로, 이를 사용할 경우 반드시 “당사 프로덕션 측정 기준”임을 명시해야 한다. 그렇지 않으면 투자자 질문 한두 번에 숫자 신뢰도가 무너질 수 있다. 둘째, 실행 전 차단·비용 한도는 2026년 기준으로 이미 여러 게이트웨이가 제공하는 기본 기능이므로, “아무도 하지 않는다”는 메시지는 전략적으로도 구식이다. Cloudflare AI Gateway와 LangSmith LLM Gateway가 제공하는 기능을 인정한 뒤, 그 위에서 우리 제품이 제공하는 “동시성 환경에서의 정확한 비용 집계와 비즈니스 단위 예산 정의”를 차별화 포인트로 삼는 것이 더 지속 가능한 포지셔닝이다.[14][15]

마지막으로, 투자자 Q&A에서는 개별 사고 사례보다 구조적 데이터를 강조하는 것이 유리하다. Teja Kusireddy의 무한 루프 사례와 Gemini·LLMjacking 사건은 매우 인상적이지만, DoiT·Mavvrik 설문조사가 보여주는 “대다수 기업이 AI 비용을 초과하고 예산 예측에 실패하며, 그 결과로 이사회 에스컬레이션과 프로젝트 취소가 발생한다”는 그림은 투자자 입장에서 훨씬 더 큰 시장 기회와 리스크를 의미한다.[9][10] 이러한 구조적 맥락 위에서, 우리 제품이 “실행 전 차단을 보다 정밀하게 수행하여 비용 폭탄과 예산 위기를 예방한다”는 메시지를 전하는 것이, 단일 개발자 사고에 의존하는 서사보다 더 강력할 것이다.
